### 已定位的缺陷与修复状态

1. **Claude 下载依赖客户端网络。** 截图编号 `89db06f2-e9a5-4339-b844-fb5951eead33` 对应 0.4.4.1，21:06:49 上报，耗时 75 秒，分类 `package_fetch_failed`，任务未上传。代码确认没有匹配的随包文件时，由客户端 HttpClient 访问 downloads.claude.ai，成功后才上传 VPS。当天 Claude 失败中 3 次为该下载分类、2 次为旧版远端 DNS 失败、6 次为 SSH 连接失败，不能混为一个网络问题。当前源码改为：随包校验文件可直接上传；否则优先由 VPS 使用其架构从官方发布服务下载并校验；仅在 VPS DNS、下载网络或超时失败时使用本机备用下载。校验失败不切换来源后继续安装。此修改共享于 Mac 和 Windows，尚未发布安装包。
2. **后续通道可能改选另一种主机密钥。** 系统更新保留原密钥并新增高优先级密钥时，新 SFTP 会选另一把，与最初确认的公钥不一致。本机真实握手复现，当前源码已限制后续连接使用已确认公钥类型，并继续逐字节核对；密钥真正替换时拒绝且不发送密码。详见 `HOST_KEY_TASK_FAILURE_2026-11-15.md`。现场诊断缺少算法与密钥，不能认定所有 SSH 失败均由此触发。
3. **挂载断线后退出受阻。** 退出要求远端同步卸载，断线时失败并保留文件桥；旧版无原地更新登录凭据的恢复入口，可能形成不能重新登录也不能安全退出的循环。当前源码已有重新认证入口，真实协议测试确认错误密码不替换旧会话、新密码恢复保留文件桥和端口。仍需真实用户端验证，不能将 22 次挂载失败全部宣称已解决。离线时如何退出并明确保留服务器待上传缓存，仍是待完善的交互。
4. **工作密码更新存在部分成功窗口。** `setup_account` 先 chpasswd，再修改 hostname 和保存 account.json，后两步失败会出现系统密码已更新、记录仍旧的状态。代码顺序已确认，早先 mock 已覆盖；本轮未改此流程，现场反馈是否触发仍未证实。代码只允许修改受管理工作用户，未发现修改 root 密码的路径。
5. **诊断阶段和错误分类仍不足。** 截图的本地下载失败被标为 remote_task；下载、主机密钥拒绝、后台恢复、退出卸载缺少独立阶段。多个账户及 CloudCLI 失败停在 package_configuring 且为通用 operation_failed，不能凭此认定 APT、磁盘或密码原因。应补固定阶段码，继续保持不上报原始日志或凭据；本轮未修改生产诊断协议。

新增测试验证 VPS 官方下载和 ARM64 架构选择、SHA256、文件权限、DNS 分类、失败后清除半成品。真实 SSH 夹具确认优先使用 VPS 返回文件、无需先请求本机 HTTP，以及新增密钥类型不影响 SFTP/隧道、替换原密钥零认证。Mac 后端编译与已有安装错误协议检查通过。当前均为源码修复和本地验证，未替换用户软件、未发布正式版本。

## 代码确认

1. 退出受阻确有对应实现。`MainWindow.cs` 的关闭流程要求 `UnmountAsync` 成功，否则保留文件桥并提示恢复连接后重试。`connect` 又会拒绝有活动挂载的重新登录。安全同步本身有必要，但恢复路径缺少重新认证入口，用户可能陷入重连失败、不能换凭据、不能安全退出的循环。
2. 重连使用 `connection.Password` 中原始登录凭据；没有原地更新凭据的入口。若服务器上的这个登录账号密码在外部变化，已有 SSH 会话可以暂时继续工作，但新建挂载 SSH、SFTP 或恢复控制连接会继续使用旧密码。此机制可以解释一类故障，尚不能证明就是本次粉丝原因。
3. `RecoverMountsAsync` 捕获异常后仅保留通用“连接暂不可用，保留挂载和缓存并继续重试”，认证失败未单独显示或上报，阻碍定位。
4. 自定义账户界面只保存本机草稿，须执行第一步“开始部署/更新”才应用；远端 `setup_account` 修改工作用户密码，不修改 root。截图显示登录用户为 root，所以如果粉丝改的是工作用户密码，root 仍用原密码属于当前设计，界面容易让人混淆两类密码。
5. 存在密码更新的部分成功窗口：`chpasswd` 在 `hostnamectl` 和 account.json 写入之前执行；后续失败会出现系统密码已更新、保存记录仍旧的情况。隔离 mock 调用已验证此顺序及失败路径，未运行真实 chpasswd。不能据此断言粉丝触发了该路径。
6. 软件内置 SSH 终端使用工作用户密钥和 `BatchMode=yes`，不使用手输密码。“SSH 里新旧密码都报错”需明确是外部终端还是内置终端，核对实际用户名和完整错误；目前没有证据证明软件把 root 密码改坏。

## 处理方向与待补证据

优先补充同端点、同指纹的原地重新认证能力，保留文件桥和待上传缓存；分别提示认证失败、网络故障、转发失败及卸载占用，并补齐后台恢复和退出阶段诊断。不要通过直接取消同步保护来掩盖恢复失败。

账户设置须明确区分工作用户密码和服务器登录密码，并处理实际系统密码与保存记录的部分成功状态。粉丝侧下一份最有价值的证据是外部 SSH 的完整报错和所用用户名（隐去密码），以及密码修改的位置；若新旧密码对同一账号均失败，还需 VPS 控制台核查 sshd 认证日志、账号状态与密码认证策略。
